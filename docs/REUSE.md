# Reuse Checklist

## Input checks and source-copy text

Test-diff reuse builds on Git file snapshots, the Python AST, the standard-library TOML/JSON parsers, and the existing filelock. Python comments and manifest description fields are recognized by comparing effective content; real dependencies, execution modes, and inputs that cannot be parsed keep full verification. A full batch stores results per test file, only fills in the affected scope, and does not extend how long a result stays valid.

JS/TS copy checks reuse the [Oxc parser](https://oxc.rs/docs/guide/usage/parser). The dev dependency is pinned to `oxc-parser@0.154.0` (MIT license), sourced from the [official Oxc repository](https://github.com/oxc-project/oxc). The project's Vite/Oxlint toolchain already ships Oxc; the standalone Node checker parses comments, strings, templates, and JSX, and does not enter the application runtime bundle. Frontend source parse errors are zero. A Tree-sitter trial produced errors on named tuple members and JSX query parameters and was not adopted; no new Python parser dependency is added. The Chinese and English criteria live in `scripts/copy-rules.json`; ambiguous wording only prompts a manual check.

## Standalone macOS build

The standalone app reuses the project's existing PyInstaller 6.22.3 (GPL-2.0-or-later, with the bootloader exception). The macOS native bootloader hosts Python 3.14 and the Cocoa menu bar, and resources and the CLI entry point follow the existing desktop implementation. The disk image uses the system `hdiutil`, so no new runtime dependency is needed. Building and signing follow the [PyInstaller macOS docs](https://www.pyinstaller.org/en/stable/usage.html) and the [Apple distribution docs](https://developer.apple.com/documentation/xcode/packaging-mac-software-for-distribution).

Peach owns the standalone data directory, first launch, build identity, and resource manifest. arm64 and x86_64 use their own Python and native extensions and are built separately per the [PyInstaller architecture constraints](https://pyinstaller.org/en/stable/feature-notes.html#macos-multi-arch-support); frozen programs are not merged with lipo. The app installs no system components and uses drag-and-drop DMG installation; the system-level install flow of a PKG is not part of this path. The source-run LaunchAgent shell keeps its own build entry point. Launch and read/write acceptance of the standalone artifact use an isolated data directory and do not touch the real ledger or the two-machine configuration.

## Hardware transcoding backends

Whole-file MP4 and HLS reuse the existing FFmpeg CUDA / NVENC, VAAPI, `scale_vaapi`, and `hwupload`, without introducing a Python command-wrapper library. The Windows release tooling is pinned to FFmpeg 9.0.2 (GPL-3.0-or-later; see `scripts/ffmpeg-sources.json` for the source manifest); the Linux image uses Debian trixie's FFmpeg, `mesa-va-drivers`, and `vainfo`, taking versions from Debian security updates and not copying driver code separately. Mesa is distributed under the upstream per-component licenses, the image size added by the drivers is determined by the build, and AMD needs the host's amdgpu and firmware. Device parameters and the hardware decode interface follow the [official FFmpeg docs](https://ffmpeg.org/ffmpeg.html#Advanced-Video-options), and the driver scope follows the [Debian VAAPI notes](https://wiki.debian.org/HardwareVideoAcceleration).

Peach keeps only device selection, the one-time synthetic-frame probe, the command attempt order, and failure fallback; the probe result is shared by the two services. The reuse search covered the current NVENC chain, the media-tool resolver, and the Git history, and found no standalone VAAPI path. FFmpeg already covers codecs and filters; wrapper layers such as ffmpeg-python provide neither device drivers nor hardware availability checks, so the project's subprocess entry point is kept and no Python dependency is added. Regression tests use synthetic input and process stand-ins to verify Linux node selection, permissions and timeouts, 10-bit to NV12 conversion, and whole-file and segment fallback. The 2026-10-19 Windows NVENC measurement used 640×360 synthetic frames for the probe, and synthetic 10-bit HEVC produced H.264 `yuv420p` through both the whole-file MP4 and HLS CUDA / NVENC paths; 128×128 does not meet the encoder's minimum size, so the probe uses 640×360 throughout. Driver initialization, decoding, and playback acceptance on the target AMD GPU were not obtained. There is no production entry point or real ledger write.

The child is created suspended, and after ownership is recorded it runs via `ResumeThread`; when creation is refused, `CREATE_BREAKAWAY_FROM_JOB` is retried only once, and when resuming the main thread fails, the child that has not run is reclaimed. Peach keeps parameters, the Peach data directory, and source and PyInstaller environment handling, and consumes the one-time handoff marker. The entry point first reuses the read-only lock probe of `SingleInstance` and opens the page directly when already running; the lock probe creates no file and does not block the child process from acquiring the lock.

The current tree and Git history already have `windows_restart`, `tray_lifecycle`, and `process_job`, and each continues to be reused for its restart, recovery, and child-service cleanup behavior. `DETACHED_PROCESS` only detaches from the console; `CREATE_BREAKAWAY_FROM_JOB` depends on the chosen parent's Job allowing breakaway; WMI, Shell COM, and scheduled tasks introduce extra services, environment handoff, or registration lifecycles and were not adopted; `pywin32` is not a runtime dependency and the monitor must load only the standard library, so native APIs are used, with no new dependency. The source tray calls the base interpreter directly and, following the `__PYVENV_LAUNCHER__` protocol of the [CPython 3.14.7 venv launcher](https://github.com/python/cpython/blob/v3.14.7/PC/venvlauncher.c), keeps the virtual-environment identity. Only the protocol is referenced; no PSF-licensed source was copied. Temporary-process regression covers multiple layers of shared Jobs, inner automatic breakaway, and the launcher's private kill-on-close Job: ordinary children exit with the launcher, while the desktop child stays alive in the shared Job and consumes the handoff marker. Unicode arguments, environment, working directory, virtual-environment identity, and process cleanup were also checked; the real Explorer is not added to the test Job. Diagnostics record only the process-member state that can be obtained and the raw limit values of the calling process's direct Job, with bit definitions reusing the [Microsoft docs](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information); when the full handle chain and owner were not obtained this is stated explicitly, and nothing is inferred through a system-wide elevated scan.

The SDK handles background HTTP, TLS, the Sentry envelope, and server-side rate limiting; Peach handles local choice, technical-field projection, aggregation of same-kind errors, and a per-machine daily cap. ## Resource indexer

`resource_search.py` uses `parse_capabilities` and `parse_torznab` of Torznab 0.2.1 (MIT, Python ≥3.10, supports the project's Python 3.14). The source is pinned to tag v0.2.1, and the project is still labeled Alpha; an offline XML POC covers caps, GUID magnets, size, seeders, peers, and duplicate tags. The PyPI package adds one direct dependency, with requests already a transitive dependency; acceptance against a real indexer needs a user-configured endpoint.

Requests reuse HTTPX 0.28.1. The SDK's own requests layer has no response-size limit and its exceptions may carry the full URL, so only its parsers are used. Peach handles the two requests per source (caps and search), at most six torrents, a 2 MiB response cap, at most four sources per round, a 45-second budget, disabled redirects, redacted errors, rejection of XML entity declarations, and size, seeder, blacklist, quality ranking, and at most five candidates. Title codes reuse `feeds.scan_code`, and identity and Chinese-subtitle and uncensored edition detection reuse `catalog_rules`. Credentials reuse `CredentialStore` with no cross-machine sync field registered; changing the endpoint does not carry over a saved API key.

It was checked against the [Torznab 1.3 specification](https://torznab.github.io/spec-1.3-draft/torznab/Specification-v1.3.html) and the FC2 query, magnet-field fallback, and partial-failure boundaries of SakuraMedia `torznab.py` (GPL-3.0, revision `9c6a31915c9a364c9d6717798575daf9445916bd`). SakuraMedia is coupled to its ORM and is not a runtime dependency. Candidates are filled into the magnet box of the cloud-download popover, and after user confirmation go through `submit_offline_download`.

OneJAV and Free JAV Torrent give only torrent links. Such entries fetch the torrent through the download proxy of the same origin as the indexer, decoded by bencode2 0.3.35 (MIT, Python ≥3.10, with a cp314 Windows wheel and a pure-Python wheel), and then the SHA-1 of the info dictionary is computed. Evidence: the hash computed from a real sukebei torrent matches the Torznab `infohash`; the Prowlarr proxy returns `application/x-bittorrent` for OneJAV and Free JAV Torrent. Both bencode2 and fastbencode 0.3.11 (Apache-2.0) reject dictionaries with out-of-order keys, so re-encoding gives back the original. bencode2 was chosen because it has a pure-Python fallback. torf (GPL-3.0) does far more than needed, and bencode.py (BitTorrent license) and bencodepy (no updates since 2015) are not adopted.

This is an implementation lookup table: which ready-made implementation carries each capability, and which part Peach itself owns. Before adding, restoring, or rewriting code, follow `.claude/skills/peach-reuse-first/SKILL.md` and check this file, the current tree, Git history, and mature external implementations first; an old filename not existing does not mean the capability is missing, and for successor relationships see "Removed legacy implementations and current successors".

The exact versions of installed dependencies are maintained by the [Python manifest](../pyproject.toml), the [Python lock file](../uv.lock), the [frontend manifest](../frontend/package.json), and the [static dependency manifest](../package.json). This page records purpose, license, and trade-offs; evidence versions and commit numbers represent only the corresponding evidence.

## Mount reachability

`mount_reachability.py` follows OpenAver's `core/source_reachability.py` (MIT, Copyright 2026 peace; pinned revision `8cc17e50453d9f69a81f5fee1a072df80f7aab73`, 2026-10-01) in adopting a normal 600-second and abnormal 60-second cadence, two-failure confirmation, and in-flight deduplication of timeouts. Peach implements this algorithm independently without copying upstream source; it uses Python 3.14 standard-library threads, events, and Futures, adding no dependency. Peach's path mapping and first directory read belong to `platform`, and the source interface, health summary, and tray share a pure in-memory snapshot; at most four directory probes are in flight, and the background thread does not block service exit.

The reference implementation's UNC TCP 445 probe was not adopted: port connectivity cannot prove that a shared directory is readable. A regular file also cannot serve as a media root, and `NotADirectoryError` is listed separately; permission denied, directory not found, and other read failures are reported separately. APScheduler is already used for scheduled tasks, but its thread executor cannot cancel a blocking filesystem call; this feature drives scheduling with a stop event and keeps directory probes that have not yet returned. MGS-exclusive releases first query the self-operated product catalog, and Prestige codes reuse the `metadata_routes.maker_sites` routing and then aggregate the group's official site and MGS images; candidates already in hand are still compared together by actual size. The general catalog is queried only when the exclusive catalog yields no candidate, so an unrelated catalog failure does not consume the whole item's budget.

Official covers and product images are chosen by pixel area; at equal size the product image is preferred, and still-frame previews keep the last tier; the image role does not let a low-resolution product image override a larger official cover.

Snapshots with only studio images continue to query the DMM catalog; only a successful DMM source snapshot skips the catalog query, and neither a CDN address built from the studio number nor the missing-memory of r18.dev replaces a DMM query.

The face cache uses `cover-face-v4` with source image size validation. `detect_cover_faces.py` automatically recomputes stale records, and per-image checks with `--refresh-faces` can decide the layout after recomputing the main face of the whole image; large covers on 4:3 or √2:1 canvases without a credible spine, or where the main face on the left clearly dominates, are framed as the whole picture. Installation, batch recompute, and restoring default framing read the same layout marker.

Traditional front covers are centered in full, proportional padding reuses the blurred backfill of the derived tier of the same image, and new releases and video-feed cards use the same framing rules. Full-spread large covers use the card's solid background, portrait ones fill by main face, and landscape ones fit completely into the container; leftover background properties are cleared on image switch.

Framing is managed by `poster-crop-v13`. The Blu-ray source title, explicit edition tags, and the image ratio together determine the 0.85 front-cover ratio, the title follows the front-cover box, and recomputing the face and the front-cover box both read the same edition; a valid wide front-cover box is also shown completely on cards without an edition title. VR markers, IENEE, IENFE, SDHS digital-release mosaics, and large covers whose credible main face crosses the DVD front-cover prior boundary keep the whole picture, passed to the card via `cover_frame.layout=still`. When two full-height seams clamp a centered front cover and the texture on both sides is below a quarter of the front cover, only the middle front cover is shown. Large covers in portrait large-image mode are centered and filled by main face, and landscape small images are shown completely, neither using blurred edge fill; spine detection for soft JPEG edges combines prominence, the left-busy-right-quiet direction, and the baseline on the front-cover side. Manual boxes keep the user's framing. The retry queue rotates by earliest attempt time, collapsed collections follow the setting skip, and per-code results are saved in `feed-cover-attempts/`. It reuses the existing HTTP, Pillow, OpenCV, and file locks, with no new dependency.

Library and new-release image fetching share `cover_artwork.metadata_snapshots` and `best_cover`, and official candidates from studio sites, publishers, R18, and DMM all take part in size comparison. Library collection treats a long edge of 1600px as the high-definition re-probe threshold, so community-reposted images can be replaced by official covers; official images of the same kind are upgraded by pixel area, and FC2 keeps the source protection of product images. `scripts/audit_cover_artwork.py` checks size, source, edition, and framing box image by image and outputs CSV; `scripts/upgrade_audited_covers.py` re-probes code by code against existing official snapshots, and `--live` supplements online through the same official chain, saving the original backup and result checkpoints. Both handle only rebuildable images and sidecars, and do not write to the ledger.

## Reuse decision gate

Every decision of "use something ready-made or write it ourselves" follows these four rules; the remaining entries in this section are concrete decisions made by them:

- First run a no-write POC on real input, then choose one of "direct dependency, pinned-source implementation, or keep in-house".
- An adopted item must record the pinned version, license, first consumer, and the domain boundary Peach keeps; a candidate dependency must not sit idle.
- Keeping in-house must record the rejected candidates and the irreplaceable constraint, not just "special requirements".
- When an external project is unsuitable as a runtime dependency but its public data model or algorithm is clearly more mature, pin a revision and use it as a reference
  implementation; when the license does not allow derivation or the source is unstable, use it only as behavior evidence and do not copy code.

Release-directory flattening and directory-ad cleanup reuse `scripts/flatten_release_dirs.py`, `catalog_rules`, and the SQLite backup.
The path plan is indexed by directory component and preserves operation order, covering assets and registered subtitles; physical moves carry sidecar files such as unregistered covers.
The directory graph excludes the file's last level; multiple subdirectories with the same name and directory wrappers with a media extension are judged as redundant levels, and the extension reuses the scanner's classification.
When a redundant directory is the sole content of its parent, two whole-directory renames and empty staging-directory cleanup are used; when the parent contains attached files or other versions, entries are merged only if the target entries do not conflict. Execution is refused when the staging location or filename conflicts.
When a wrapper directory occupies the content's target name, that directory is staged first and the content moved out, while other versions stay in place.
Each move first rechecks the real directory, a partial failure immediately restores that entry, and a ledger transaction failure restores the batch.
No new dependency; the Python standard library's path operations and SQLite already cover the underlying capability, and Peach keeps the criteria for redundant names, ads, and ledger consistency.

Full directory categorization and placement uses `scripts/organize_library_dirs.py`, reusing `organize._rename`, the directory flattening entry point, the code parser, entity categories, and the process lock. The plan is frozen by default, and only `--apply --backup` executes it; `--batch` saves the plan and receipt separately and failures are recoverable. `--stage flatten` generates its own flatten review CSV. Confirmed works in the same directory and cover images missing a studio are handled as a whole package; mixed directories move only known file groups and their paired subtitles, physical files are deduplicated, and unknown videos, conflicting identities, and overwrite targets are all kept; sidecar files in the same directory are determined by `scan.is_sidecar`, titled ones follow their video, bare `poster`, `movie.nfo`, and `extrafanart` follow only when all videos in the directory are moved, and registered and quarantined files are left alone. Source directories that cannot be deleted are recorded with their remaining names in the receipt's `cleanup_errors`. A creator target keeps only the structure below the canonical-name level, container directories above the canonical name are discarded, and when the path has no canonical name only the source directory name is carried; container directory names that are not renamed as a whole are in `resources/naming/container_directory_words.txt`. `--rollback` undoes committed entries in reverse order of the receipt, reusing `restore_entry`, and entries whose ledger has since been modified are reported separately and left untouched; without `--apply --backup` it only lists the plan. Release sites, quality, and part markers in directory names reuse `release_code_from_filename`; the date-style separator matching of 1Pondo reuses its official work-number parsing and does not merge date-style numbers across studios; the target code directory is first aligned with an existing equivalent directory, and when several coexist the official-site work-number spelling is used. When a video filename carries its own number that is not the same work as the ledger code, no directory is built and it is recorded as pending confirmation. FC2 release directories may use the `FC-` shorthand with a title appended; `@fc编号_分片` (the `@fc<number>_<part>` pattern) lacking a code checks both the parent directory number and the studio, and the directory number is not written back to the ledger. Korean MIB is placed by studio. When a unique creator relation exists but the sub-category is unconfirmed, it goes into the generic `创作者` ("creator") directory without promoting the identity candidate. Path sync covers assets and registered subtitles and does not backfill ground-truth fields.

PikPak WebDAV same-source moves are provided by `organize_clouddrive.py`, and the directory entry enables it only with an explicit `--pikpak-webdav --location pikpak --batch`. It reuses the token already stored by CloudDrive and the authentication header of the official `GetDownloadUrlPath`; the origin is fixed at `https://dav.mypikpak.com`, and authentication is not written into addresses, logs, or the ledger. The protocol follows the [official PikPak WebDAV notes](https://mypikpak.com/zh-TW/help-center/connected_apps/webdav/how_to) and [RFC 4918](https://www.rfc-editor.org/rfc/rfc4918), the HTTP client reuses the declared `httpx`, and message encoding reuses the declared `protobuf`, adding no dependency. The official `GetSubFiles(forceRefresh=True)` reads the full directory level by level from the source root, checking each level's member source, parent directory, duplicate names, and size. Same-parent renames use the official `RenameFile`; cross-directory moves within the same source that keep the original name use the official `MoveFile` with the conflict policy `Skip`, explicitly disabling cross-cloud moves and recursive merges. WebDAV only creates the required parent directories with HTTPS `MKCOL`, and both renames and moves go through the official interface. When the official side returns false or a rejection code (`INVALID_ARGUMENT`, `PERMISSION_DENIED`, etc.) and the directory confirms the original is still present and the target has not appeared, that entry is recorded in the receipt's `failures` and rolled back, and a resumed run skips it; the batch is aborted only when the original and the target both exist or both do not. `organize._rename` refuses the A drive by default and allows it only when the officially verified rename is injected through `organize.verified_renames`; when not injected, every execution entry refuses the whole batch. A single HTTP response is capped at 2 MiB, and traversal at 10,000 entries. After a move is submitted, only the caches of the directories involved are refreshed, path and size change evidence is obtained along the full ancestor chain, and then it is handed back to the existing ledger transaction; there are at most four read-only confirmations, and the move is not submitted again. When the state is uncertain the intent receipt is kept and execution stops, and even a success response must obtain complete member-change evidence. Flattened directories on the A drive use staging names that do not start with a dot and keep the same recovery receipt; the R drive does not enter this transport path.

Same-parent directory renames on the A drive reuse CloudDrive's official `RenameFile`; operations that change parent and name are split into a same-parent `RenameFile` and a name-preserving official `MoveFile`, with the intermediate path entering the recovery receipt and overwriting forbidden. Each step checks the full members and sizes; a success response does not replace path verification. `@` in paths is kept as a URI path character, and other characters use UTF-8 percent-encoding. When the authentication sample has already been moved, at most two other in-library image samples are queried, extracting only the existing authentication and not reading media content.

Banners, logos, and navigation images in promotional web-resource directories enter the review queue through `web_batch._attachment_junk_reason`. The criteria require together `_files`, URL promo boilerplate, a domain, a navigation-element filename, and a size cap; an inherited work code does not exempt web navigation images, and work images, subtitles, NFOs, and ordinary `_files` directories are kept. Fixed-name promotional attachments (installers, promo videos, QR-code cards, download-site banners) are collected by extension, size cap, and full name in the word list `resources/junk/promo_attachment_names.json` and read by `web_batch._promo_name_reason`; a hit counts only toward the review tier `JUNK_REVIEW_SCORE`, and promo directories of videos with unprobed duration, promotional creator slots, and size evidence likewise reach only the review tier; such scores alone cannot reach the default auto-move-to-trash threshold `AUTO_TRASH_SCORE` of `trash_junk.py`, and nothing is moved to trash or deleted by name alone. Permanent deletion still goes through `trash_junk.py --purge --review-csv` and `purge_assets`.

Ordinary work images and `images.rar` are kept. Deleting small files over CloudDrive WebDAV reuses the native `Path.unlink`: when a same-directory quarantine rename reports WinError 50, files up to 1 MiB are first fully backed up to `generated/purge-staging/` with the standard-library `shutil.copyfile`, recording the original path, size, and SHA256, and then deleted. If the database fails the backup is restored, and retired after commit; large files continue to report a block. This path adds no dependency, and backup and restore are managed only by `purge_assets`.

English media filename tokenization reuses `wordninja-enhanced==3.2.0` (MIT, released 2026-09-04, Python ≥3.9, pure Python, 11.4 MB wheel, no transitive dependencies). The source was read through `opensrc path pypi:wordninja-enhanced@3.2.0`; the original wordninja is older in release, and the enhanced version offers punctuation preservation and a supplementable dictionary. `space_media_names.py` first produces a per-file review CSV, inserts only spaces, keeps ordinals, characters, and extensions, and infers no person or provenance; real files in the specified directory are verified and then reuse `organize.apply_plan`, the SQLite backup, and the rollback log. Domain vocabulary is in `english_filename_words.txt` (pinned with extra weight, entries should be few: each extra entry lowers high-frequency words such as `a` and `of`), and concatenated strings often mistaken for words are moved out of the word-frequency table in `english_filename_nonwords.txt`. Apostrophe contractions, all-caps abbreviations, domains and site numbers, and hexadecimal viewkeys are not split; Cyrillic look-alike letters count as Latin letters for split points while the original characters are kept. Executed batches use `--recompute-batch <log>` to recompute the review CSV by original names and then go through `--apply --review-csv`.

Junk quarantine on the A drive uses the short name `peach-purge-<32-digit UUID>.peach-quarantine`, and the scan entry skips only this exact format; ordinary media and other `.tmp` files still need review. Quarantine restore and the full local backup keep the transaction boundary of `purge_assets`.

Original-file forensics for A-drive promotional attachments reuses CloudDrive's official `GetDownloadUrlPath` local original-file proxy, without going through Peach transcoding and without passing authentication to other sources; the actual QR-code copies and video forensic frames are in the library review output.

Keeping in-house is not a permanent exemption: when constraints change or candidate implementations are updated, rerun the POC, and this table's conclusions are not a reason to skip an external search.

## Static checks

Windows media subprocesses reuse the Python standard library's `subprocess.CREATE_NO_WINDOW`: library probing, frame extraction, sheet assembly, previews, follow covers, and media repair all set it explicitly, and output capture, timeout, and cancellation follow each entry point's original contract. The flag is natively supported by Windows and introduces no dependency; see the [Python docs](https://docs.python.org/3/library/subprocess.html#subprocess.CREATE_NO_WINDOW) and the [Windows creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags).

Frame extraction and sheet assembly fully decode the output image with the existing Pillow 12.3.0 (HPND) and do not infer validity from the compressed file size. They reuse the existing FFmpeg, color-metadata retry, and `support_bundle`: failure records include the sample second, duration, exit code, timeout, tool source, and the error output of each attempt, with the error text truncated and redacted. The diagnostic ZIP collects processing status, the most recent 8 problem lists, and startup, update, and tunnel evidence, reading at most the last 96 KiB of each file, and media names stay on the local machine. Valid JPEGs under 1 KiB, Chinese paths, failure retry, and diagnostic export all have regression; FFmpeg parameters follow the [official docs](https://ffmpeg.org/ffmpeg.html), command wrappers such as ffmpeg-python are not introduced, and the real ledger is not written. For the verification scope see [log and diagnostics verification](DIAGNOSTICS.md).

Windows FFmpeg 9.0.2 statically links VideoLAN dav1d 1.5.4 (BSD-2-Clause, official source 1,038,852 bytes, Meson + NASM, supports Windows x64 and 8/10-bit AV1). The version, HTTPS source, and SHA256 are pinned in `scripts/ffmpeg-sources.json`, and the source and license ship with the corresponding source archive; the FFmpeg binary of the full tools grows by about 3 MiB, and no Python runtime dependency is added. The native `av1` wrapper depends on hardware decoding, and browser playability cannot serve as evidence of FFmpeg software decoding; CPU decoding directly adopts the maintained dav1d, and the libaom encoder library is not introduced for a pipeline that currently needs only decoding. Release acceptance uses a synthetic AV1 clip to confirm CPU decoding and frame extraction. Build parameters follow the [FFmpeg libdav1d docs](https://ffmpeg.org/ffmpeg-codecs.html#libdav1d) and the [VideoLAN pinned release source](https://download.videolan.org/pub/videolan/dav1d/1.5.4/).

The frame extraction and AV1 software-decoding regression on macOS CI uses native tools provided by the [Homebrew FFmpeg formula](https://formulae.brew.sh/formula/ffmpeg), installed with non-core test domains; the actual version and decoding capability are checked against the install log and media regression. Windows CI keeps the pinned-version setup-ffmpeg, and release packages continue to use self-built tools; no Python dependency is added, and no production entry point or real ledger is changed.

Python reuses MIT-licensed [Ruff](https://docs.astral.sh/ruff/) 0.17.0, with the version pinned by dev dependencies and `uv.lock`. Rule configuration is in `pyproject.toml`; the official entry scans all of the repository's own Python files through `tests/test_python_lint.py`, checking Pyflakes, the Pylint error rules Ruff supports, and four common behavior hazards. Ruff's Pylint rule coverage is partial; problems requiring cross-module inference are still verified by the corresponding behavior regression.

The existing Oxlint 1.85.0 correctness, `eqeqeq`, and `oxc/no-accumulating-spread` are reused, adding no dependency. Source and tests share the base rules; the shadcn design rules apply only to the project's own React source.

The MIT-licensed [anti-slop](https://github.com/dmmulroy/anti-slop/tree/c44ef22ca116d0ba62a3ff663a0bd13a3f3fa40b) was evaluated. In a trial run at the pinned commit, 7,274 of 8,243 diagnostics demanded blank lines; its rules forbidding `unknown`, runtime `typeof`, and module mocks do not suit this project's input validation and test doubles, so the whole plugin is not introduced. Type safety is checked jointly by TypeScript, the base lint, and the corresponding behavior regression.

## Taste sources and preferences

Bookmarks reuse `beautifulsoup4==4.15.0` (MIT, an existing dependency) to parse Netscape HTML, JSON and timestamps use the Python 3.14 standard library; Firefox reuses the existing SQLite consistent snapshot, and the private source, stop-reading, upload, and delete entries keep the history module's. Browser formats follow the `roots/children/type/url/date_added` of Chromium's `BookmarkCodec` and the `moz_bookmarks/moz_places` of Mozilla Places, with no external implementation code copied. Isolated samples cover HTML entities, missing dates, duplicate URLs, non-HTTP(S) filtering, standalone Chromium bookmark data, the Firefox snapshot, and failure retention; interface and preference tests use a temporary database, with no new dependency or ledger migration.

Title topics reuse the Chinese-English-Japanese content word list of `genre_taxonomy`, the longest match of `pyahocorasick==2.3.1`, and the existing canonical-identity alias index; Peach keeps title abbreviation filtering, English word boundaries, adult context, and synonym dedupe between URL and title. Isolated samples cover ID-only detail URLs, title names and aliases, Rule34 tag cross-evidence, full-width/half-width, negative conditions, and false matches on ordinary pages; the original pages are not requested, and no tokenization or model dependency is added.

Candidate review (2026-10-17): [browser-history](https://github.com/browser-history/browser-history) is Apache-2.0, pure Python, cross-platform, and dependency-free, but its bookmark capability is explicitly marked experimental and not covered by tests, and its generic reading copies files first, so it cannot directly replace Peach's consistent snapshots and failure-retention policy; [bookmarks-converter](https://github.com/radam9/bookmarks-converter) is MIT and declares support for Windows/macOS/Linux and Python 3.14, but its HTML path depends on BeautifulSoup and its conversion model also brings in SQLAlchemy. Peach needs only flat URLs, titles, and possibly missing dates, so it carries generic parsing with the existing BeautifulSoup and the standard library, keeping a minimal format adapter and the private-evidence policy. Raw input is read only locally, and no network traffic is collected.

History snapshots and import reuse the SQLite backup API and the Chromium, Firefox, and Safari adapters of `browserexport==0.4.4`. `taste_browsers` manages local profile directories and enabling/disabling, with configuration inside the private history database; disabling keeps the data already imported, and one profile failing to be obtained does not block the others. For source rules and account association see [taste sources](TASTE_SOURCES.md), which only reuses existing entity links and enabled follows and does not confirm new identities on its own.

Multi-dimensional preferences reuse behavior weighting, genre normalization, and the MMR of `related.rank_related`; `taste_preferences` stores canonical identity, evidence kind, and candidate strength. The persistent cache reuses `fsutil.atomic_write_text` and is invalidated by ledger, history database, and rule source version, and read-only history connections ignore a WAL with no data frames. Name scanning adopts [pyahocorasick 2.3.1](https://github.com/WojciechMula/pyahocorasick) (BSD-3-Clause, Unicode, Python 3.12–3.14, Windows/macOS/Linux); the pinned C implementation was read, and the Windows CPython 3.14 wheel installs and passes; this is the only new direct dependency. Long titles, multiple aliases, overlapping names, and ASCII word boundaries are constrained by Peach. A real read-only summary covers seven dimensions; preference candidates and the private cache do not rewrite the ledger.

## Library processing control and time estimation

Resuming long-running tasks reuses the local atomic records of `job_recovery`, `BackgroundJob.checkpoint`, and `TaskRunHandle.checkpoint`. The main task keeps the original `job_id`, `run_id`, start time, processing scope, and domain checkpoints; successor reordering keeps the original progress. Scanning reuses the existing `os.scandir`, SQLite batch commits, `filelock`, and `fsutil.atomic_write_text`, saving the traversal stack, filename cursor, and subtitle pairing data. Local metadata is saved as small evidence sidecars per movie, and the metadata-complete set is committed only after candidates are successfully written to disk; organizing atomically saves the log of the same batch item by item. `scrape_codes.py` reuses streaming CSV and raw source snapshots, and a resumed run keeps only codes confirmed complete, so unfinished codes can be replayed.

The current tree, the Git history of scanning and collection, and the existing task queue have all been checked; no new scheduling or workflow dependency is introduced. The project's pinned APScheduler 3.11.3 (MIT) handles dispatching, and its persistent job store records scheduled jobs and cannot save how far a function got through movies or source pages, see the [upstream scheduling notes](https://apscheduler.readthedocs.io/en/3.x/userguide.html#adding-jobs). Result replacement keeps the Python 3.14 standard library's [`os.replace`](https://docs.python.org/3.14/library/os.html#os.replace) (PSF), and locking keeps the project's pinned `filelock`, adding no runtime size or platform requirements. Isolated evidence covers interruption between directories and within a directory's batch, the follow backfill cursor, a fixed source set, original task identifier and counts, candidate CSV retention, and the organize log of the same batch; it reads no real media, accesses no external collection sources, and writes no real ledger.

Scanning, probing, metadata requests, and the nine grid reuse `process_library`, `scan_location`, `SourceTransport`, `frame_capture`, and the existing movie checkpoints; task recovery keeps `BackgroundJob`, `job_recovery`, and `task_run`, and the user's pause intent is persisted separately. The current tree and the Git history of `library_processing.py` have been checked; install pause is used only for install transactions and cannot directly represent a user pause. The Python standard library's `threading.Event` and `contextvars.ContextVar` provide wait wake-up and current-task isolation, follow the project's Python version, are cross-platform on Windows and macOS with no extra dependency size; the license is PSF, and the official docs and implementation are at [threading](https://docs.python.org/3/library/threading.html) and [contextvars](https://docs.python.org/3/library/contextvars.html). The existing APScheduler 3.11.3 is used for timed dispatch and cannot pause a function that has entered a media read, so it does not carry the safe stop points. Isolated tests use a temporary ledger, a paused thread, and a simulated clock to verify safe stop points, cross-restart intent, low-occupancy intervals, and pause budget compensation, reading no real media and sending no external requests.

`processing_control` keeps Peach's phase, mode, and time-estimation policy: startup only totals the ledger file count and size, preferring the local machine's completion times for similar work; unknown additions are explicitly not in the initial scope. The remaining time for the whole run adds the current phase and the phases yet to run; the current phase uses the most recent 20 completion increments, and later phases use conservative rough estimates. Files with no code and no NFO are not counted toward external collection after the same-directory check completes; when a task stalls, the read endpoint withdraws the old estimate. Processing intensity is low-occupancy, standard, and high: low-occupancy uses single-thread FFmpeg and a larger per-item interval, standard uses two decode, filter, and encode threads and a short interval, and high uses the tool's automatic threads with no extra interval. amane queries site by site at low occupancy, and the rest keep the existing scheduling; all tiers respect source rate limits, and the single-asset pipeline and pause checkpoints are shared. Intensity applies only to the current task, historical durations are normalized by tier coefficients, the scope at start and at switching is a rough estimate, and actual samples continue to calibrate. The persistent state does not modify the ledger schema or change production entry points.

Companion images keep Pillow 12.3.0 (MIT-CMU) decoding and `install_cover` registration. File reads and JPEG conversion for cloud-drive and unknown sources run in a separate subprocess, which is terminated after a 20-second timeout and awaited for exit before a retryable problem is registered; sources declared as local disks are decoded directly in the thread, without starting a process per image. Isolated tests use a Unicode-path image, an invalid image, and a real timeout subprocess for verification. Process timeout reuses the project's Python 3.14.7 standard library [`subprocess.run`](https://docs.python.org/3.14/library/subprocess.html#subprocess.run) (PSF license, no new install size), hides the window on Windows, and the source module and the standalone-package CLI share the conversion function. A thread wait timeout cannot terminate a synchronous file read, so cloud drives do not use a plain thread wrapper; FFmpeg is already used for media tasks, but single images still reuse Pillow, adding no decoding dependency.

Directory listings and `SidecarIndex` are reused within a run, with a filename index built once per directory; same-name, shared NFO, and numbered-image ownership keep `library_nfo`. In an isolated fixture of 500 videos and 1,000 directory entries, item-by-item matching took about 1.01 seconds and the reused index about 0.007 seconds with identical output; this figure reflects only filename matching and does not represent cloud-drive reads or whole-run time. Media attribute probing for companion images and free sources reuses the standard-library `ThreadPoolExecutor`, the three tiers taking 1, 2, and 4 items respectively and backfilling when idle, with the main thread saving results and passing through the pause stop points; the media-read limits of billed sources and each metadata site's rate limits keep their original policy. Different phases still advance by their actual dependencies, and the UI steps only display these boundaries.

`_RemoteSession` reuses, by source and code, the original evidence newly obtained in this run and explicit "not listed" answers; retrying the first asset with the same code obtains a new answer, and the other assets share it. Source errors and timeouts can still be retried and are not recorded as not listed. Reused results generate candidates per asset, fields still go through the existing source and conflict criteria, and other assets' ground-truth fields are not copied directly. Custom-source configuration is read live, and disabling and field-mapping changes take effect immediately.

The waiting time on cards and the task popover starts from the server snapshot and advances the current text every second with the browser's monotonic clock. A new snapshot resets the starting point, and pause, finish, and unmount clear the timer; the per-second re-render is confined to the progress subtree and does not change the two-second status request. Component tests check consecutive seconds, request counts, reset on file change, and unmount cleanup, and desktop and mobile browsers verify the actual ticking.

The task card reuses Sonner 2.0.8 (MIT)'s `toast.custom`, stable task ids, and infinite duration; the two stacks `processing` and `receipts` are routed by `toasterId`, and ordinary receipts avoid the task panel by its measured height. The task stack enables `expand` to keep automatic height, with detail opening and closing managed by the card; collapsing hides only the body, and pause, speed, and the time estimate stay visible. The server `steps` update at actual processing boundaries, and completed steps are shown with a checkmark and strikethrough. The failure popover auto-shows only an end state observed this time or a result within two minutes, an old failure snapshot does not pop up automatically, and once the user closes it, it stays closed. React Aria 1.22.1's Slider, Popover, and the existing BoardUI Button carry keyboard, focus, and popover behavior, with the three tiers corresponding to `low/standard/high`; the top tier's glow uses SVG and CSS, unmounts after the popover closes, and stops motion when paused or in a background page. For the basis and differences of the UI rebuild see [control evidence](reference-snapshots/processing-task-controls.md). No new dependency. Problem details keep `state/library-processing-<job_id>.issues.jsonl`, and a new task keeps other tasks' details.

The site accent-color check covers progress, focus, selected states, action buttons, and glow: the old `--feedback-success` references the existing accent color scale; RSS subscription keeps orange, and info, success, warning, error, brand, and chart categories keep their semantic colors.

Ordinary Toasts and the scan task card share the Agent Progress frame, with the 16px radius resolved by existing tokens inside the notification stack, and the thin border and contact shadow reusing `border-button-default` and `elevation-xs` respectively, without changing content layout.
