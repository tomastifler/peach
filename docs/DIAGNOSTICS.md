# Logs and diagnostics

This page describes the boundaries of exception logging, browser error reporting, diagnostic export and optional remote diagnostics. Normal cancellation, cache fallback, source misses and task mutual exclusion each keep their own state.

Environment and fault evidence is produced by one set of collection and classification functions, and each output entry takes fields by purpose: `reporting_identity` provides program, build and host scale, `diagnostic_exceptions` provides the structured error codes and media failure categories of the exception chain, and `diagnostic_context` normalizes browser, playback and runtime state. Output entries do not re-identify the same fault on their own.

| Output | Scope of use |
| --- | --- |
| Local logs | Sanitized exception chains, error codes, browser and playback scene, request arrival and response media type |
| Diagnostic ZIP | Summarizes bounded evidence from local logs and the current runtime state; keeps collection failures and not-obtained states |
| Remote technical diagnostics | Projects only the declared code locations, build identity, structured error codes and fixed failure categories; detailed browser and playback scene stays local only |
| Version statistics, population research | Reuse the program and build identity, each obeying its existing field, switch and frequency contracts |

Desktop artifact acceptance explicitly turns off version statistics and error upload in a temporary Peach data directory, and keeps them off in the first-run submission, so synthetic tests do not enter official telemetry.

## Feedback channels

When library processing fails, retry the failed items, then get the ZIP from the tray's "Export diagnostic report" or the system diagnostics page's "Download diagnostic report". The user needs to provide only one ZIP. In desktop deployments, downloads are limited to the machine running Peach; Docker deployments allow logged-in private-network clients to download, and reject proxy forwarding. When the web page is unavailable, generate the ZIP inside the container following [Docker diagnostic export](DOCKER.md#exporting-a-diagnostic-report). Logged-in same-origin devices can report browser errors; open access mode provides no anonymous remote reporting.

The underlying evidence must actually be recorded when an error occurs. The full issue list is at `state/library-processing-<job_id>.issues.jsonl`. The generic issue list cannot reconstruct a discarded FFmpeg error; historical failures without a raw record must be retried to collect evidence.

The diagnostic ZIP reads up to a full 16 MiB of a JSON state file, then sanitizes it by field after parsing. Each state file's exported content is at most 96 KiB; when reduction is needed, task identifier, state, stage and counts are kept first, then steps, issue previews and other fields are included. A reduced collection keeps at most the first 20 items, text at most 4000 characters, and nesting at most 8 levels; when fields still do not fit, the item count of collections is reduced further. JSONL issue lists read the last 96 KiB and export only recent records that parse completely; a truncated first record, corrupt records and records exceeding the post-sanitization size limit are not exported. Media names, paths and credentials follow field sanitization.

The `logs` manifest of `report.json` records each file's `source_bytes`, `exported_bytes`, `status` and `truncated`. JSON field reduction is marked `projected`, and records `omitted_fields`, the number of top-level fields not included, and `collection_counts`, the original sizes of collections among the first 64 top-level fields; a top-level array uses `collection_count`. JSONL uses `skipped_records` to record the number of records within the read range that were not exported, and a truncated first record is not counted. Cases such as empty JSON, corrupt JSON, exceeding the read limit and no valid records record only the manifest status and generate no empty file.

| Manifest status | Meaning |
| --- | --- |
| `included` | Valid content exported; whether it was reduced is shown separately by `truncated` and `projected` |
| `empty_json` / `empty_jsonl` | The JSON is blank, or the JSONL is zero bytes |
| `unreadable_json` / `invalid_json_shape` | The JSON cannot be parsed, or the top level is neither an object nor an array |
| `json_size_limit` / `json_depth_limit` | The JSON exceeds the full read limit, or nesting is too deep during parsing or sanitization |
| `json_projection_limit` | After field reduction the JSON still cannot keep valid content within the size limit |
| `no_complete_records` | No exportable complete records within the JSONL read range |

## Evidence chain

| Path | Persistent evidence and verification |
| --- | --- |
| Startup, CLI, tray | Exception hooks are installed before configuration and optional dependencies load; main thread, background threads, unraisable, asyncio and warning/error logs are written to `errors-*.log`, native faults to `crash-*.log`; a fallback directory is used when not writable |
| HTTP requests | Unhandled exceptions and HTTP 5xx record the traceback, method, route template, status code and `error_id`; the response header `X-Peach-Error-ID` links to the record; request parameters, body and auth headers are not collected as context |
| Background tasks | Exceptions record the task key, job/run number, thread and traceback; operations that explicitly return failure record the failure message; pause, mutual exclusion and cancellation follow the task protocol |
| Frame extraction, tiling, probing | Keeps the exit code, timeout, sampling position, duration, tool source, color retry and bounded stderr; `media-probe`, `preview`, `frame-capture`, `frame-tile` and `library-preview` cover each entry |
| Image validity | Full Pillow decoding confirms an image; a small solid-color JPEG is usable, while fragments, non-zero exits and stale outputs cannot count as successfully generated |
| External sources, downloads | Source authorization, rate limiting, cooldown and misses use domain states; unexpected failures use the existing exception logs and task receipts; the ZIP contains source health state and time, and raw source responses stay local |
| Follow checks, media proxy | `follow-check` and `follow-media` local events record the source, source and item numbers, failure stage, operation and the upstream status code when available; media events distinguish the post source from the resource source, and exception chains and code locations are exported with the support package. Addresses, credentials and private paths are sanitized uniformly, upstream response bodies are not recorded, and remote diagnostic fields are not widened |
| Updates and rollback | Install and rollback failures keep the traceback; the ZIP contains startup preparation, update state, source update log, tray restart log and recent migration logs |
| Tunnel | The ZIP contains `cloudflare-tunnel.log` and sanitized runtime state |
| Browser | Saves message, stack, script file name, line and column, page and browser identifiers; query parameters do not enter page fields; same-origin, valid login, per-minute count and request size gates have regressions |
| Media tools | The diagnostic report and ZIP check the actual version, executability and the AV1 software decoder; tool failures keep the existing error classification locally, including missing media, permission, disk headroom, invalid media and decoder unavailable, and full-path sanitization does not affect that classification; `/healthz` uses only lightweight path checks and runs no external tools |

## Local diagnostic snapshot

`report.json` summarizes the following technical evidence. When downloaded from the system diagnostics page it carries the current browser snapshot; tray and CLI exports extract the already recorded browser and playback context from recent local error logs. A browser environment that was not recorded is marked `unavailable`, and it cannot be used to judge that a browser or codec is unsupported.

| Scope | Fields and sources |
| --- | --- |
| Program and system | Program version, distribution method, frozen build commit and time, source checkout commit, Python, OS version and Windows edition type, architecture, process relationships, logical core count, memory tier, active thread count, SQLite and key runtime dependency versions; a source commit does not prove the running process has loaded that version |
| Configuration and storage | Listening address category and port, hosting method, sync and tunnel switches, whether proxy environment variables exist, data disk total and headroom, existence state of runtime directories, media preview and playback acceleration preferences |
| Browser | User-Agent, brand, full version, platform version and architecture from client hints, language, time zone, secure context, online state, availability of cookies and local storage, viewport, pixel ratio, touch points, logical core count, the memory tier the browser provides and the readable WebGL graphics vendor and renderer; detailed client hints wait at most one second, and when restricted or unsupported the reason is kept |
| Playback capability | Native `canPlayType()` and MSE capability claims for H.264, HEVC, AV1, VP9, AAC, AC-3 and Opus; whether MediaSource and MediaCapabilities exist. A capability claim cannot prove that specific media decoded successfully |
| Playback failure | Native error code and reason, network and ready state, playback position, duration, size, buffers, playback settings, source protocol, same-origin state, and the status, elapsed time and byte count of the last eight media requests |
| Server-side playback | Media request arrival records, Range, playback plan, the media type actually declared by the file response, cached codec and pixel format, duration, file generation, hardware policy and existing probe results; diagnostics do not read media separately or trigger transcoding |
| Checks and tasks | Detailed database and migration state, access protection, port state, recent failed task numbers and times, sanitized mount state, source health state and existing processing, update and delivery receipts |

Browser and playback context is written only to local logs and does not enter the remote reporting entry. The shared package contains no accounts, cookies, credentials, full media addresses, URL query strings, media names or library lists. Records have a field whitelist and size limits; logs are exported by the existing tail limit, and the summary holds at most eight browser snapshots and twenty playback records. Requests that have not completed do not appear in Resource Timing, and should be judged together with the server-side arrival records. Tool unavailable, storage read failure, unsupported capability API and not yet probed each keep their own state or reason.

The same browser environment is recorded once per minute, and the environment snapshot is independent of the budget of twenty errors per minute; frequent refreshing does not use up the error record quota. An explicit download keeps the current client's snapshot.

The `server_timezone` of project logs and the ZIP records the service host's actual time zone name, UTC offset and local time with offset; the browser's `timezone` and `utc_offset_minutes` independently record the accessing device's actual environment. Offsets are positive east of UTC, for example UTC+8 is `480`. The log's `at` uses UTC for easier sorting, and `server_timezone.local_time` is the corresponding local time; the service host's time zone cannot stand in for the client's. When the time zone name is not obtained, the offset, local time and the read failure state are kept, and no guessed time zone may be filled in. The task recovery scheduler uses UTC only for fixed-interval scheduling and does not decide the time zone of the diagnostic environment.

Access logs keep known media routes, API routes, the HTTP version and response status code; URL query strings are removed entirely, and unknown paths stay hidden. `206` only means a range response was sent, and cannot prove the browser finished decoding.

## Optional remote diagnostics

The installer, first-run setup and the settings page "App and maintenance" offer a single option, "Send version statistics and error diagnostics (recommended)". It is checked by default, controls both version statistics and error diagnostics at once, and can be unchecked or turned off in settings. Silent installation keeps an existing choice. The choice is stored locally in `state/remote-reporting.json`; when there is no record both are on by default, a saved opt-out stays in effect, and a corrupt record or one with only one of the two enabled sends nothing. Nothing is written to the ledger. When there is no receiving endpoint the page states clearly that nothing will be sent, and the choice can still be saved.

| Category | What is sent and how it is filtered |
| --- | --- |
| Version statistics | Peach version, distribution method (`windows-app`, `macos-app`, `docker`, `wheel`, `source`), OS type and version, CPU architecture and logical core count, memory tier, Python version, runtime environment, source/standalone package form and the public build commit, at most once per machine per UTC calendar day; attempted at process startup, with no installation identifier, so independent users cannot be counted from it. Memory takes the nearest common capacity tier; inside Docker the OS version is the host kernel, and the host OS of Docker Desktop is distinguished by the kernel name |
| Python errors | Version, distribution method, platform, Python, CPU architecture, failure stage, layered exception chain, Peach and whitelisted framework file names/function names/line numbers, structured error code; error text, variables, source context and user directories are not sent |
| HTTP 5xx | Appends method, route template and the correlated error number; no instance parameters, query parameters, body, auth headers or user URLs |
| Media tools | Exit code, and categories of a definitely matched missing AV1 decoder, illegal media, permission, disk space or unknown decoder; stderr and media names stay local |
| Browser errors | Whitelisted exception types, the line and column of Peach's official script and the public build mapping ID; errors without a locatable stack and extension scripts are not sent |

SQLite errors reuse the structured error codes of local and remote; when determinable, a fixed category of missing table, missing column, locked, read-only, corrupt or unable to open is attached, and no table name, column name or SQL is sent. Media failures extract a fixed category before path sanitization, and the stderr carried by a subprocess exception itself also takes part in classification. When the system does not support a folder dialog, the local state is kept; on supported platforms, a dialog that fails to start still enters technical diagnostics.

The remote event count means the report batches stored by the receiver, and `occurrence_count` means the number of occurrences that batch represents. Daily budgets, turning off upload, network loss and filtering cause missing observations; not receiving an event cannot be interpreted as no fault. Version statistics are once a day without an installation identifier, and cannot be used as the denominator for independent users, daily actives or fault rate. An error event carries the service host's environment, and the client system or browser accessing the page cannot be inferred from it. Research snapshots and version statistics are both ordinary events and still use the receiving platform's event quota; quotas are not isolated by project at the organization level.

An event's `purpose` distinguishes `version-statistics`, `technical-diagnostics` and `population-research` of the separate research channel. The fault view uses `level:error purpose:technical-diagnostics`, and production faults can add `environment:production`. Historical events without a purpose tag must be reviewed separately, and their source is not inferred from missing fields. Startup statistics are ordinary info events and should be excluded from the fault view and alert conditions.

`environment` accepts only `production`, `development` and `test`; standalone packages and ordinary source deployments default to `production`, Git isolated worktrees default to `development`, and `PEACH_REPORTING_ENVIRONMENT` can specify it explicitly. `runtime` is `packaged` or `source`; `dist` uses the build commit, and local directories, hostnames or free-text identifiers are not sent. The standard test entry turns off this process's telemetry and passes `PEACH_REPORTING_TEST_MODE=1` to subprocesses, blocking real outbound sending on both channels at the final HTTP request boundary; the in-memory receiver can still verify the final payload.

Exception chains are saved per Sentry's cause-first, outer-last order, with each layer keeping its own frames. Framework frames accept only `asyncio`, `anyio`, `starlette`, `httpx`, `sqlite3` and `urllib3`, projecting only the module and code location; the log entry still requires a Peach frame to be included. SQLite faults carry an integer error code and the `SQLITE_*` error name, without SQL, table names or the original error text.

When the same exception instance and the same traceback are observed by several forensic entries, it is counted only once; when the same instance is re-raised forming a new traceback, it is still counted. When a browser has no stack but provides the official bundle file name and positive integer line and column, it can also be located; generic errors lacking this evidence stay local.

The official frontend build produces matching JavaScript, source maps and a deterministic Debug ID in `build/sentry/browser/`, public `web/dist` contains only the official JS/CSS, and page routes do not distribute maps. The build plugin disables telemetry and automatic upload. Maintainers run `npm --prefix frontend run build` at the project root to produce this build's mappings; only after explicitly configuring `SENTRY_AUTH_TOKEN`, `SENTRY_ORG` and `SENTRY_PROJECT` does running `npm --prefix frontend run sentry:upload` upload. Before uploading, check that the private JS and the distributed JS are byte-for-byte identical and that the map matches the Debug ID. The mappings contain the build sources of the app and its dependencies, and no run logs, library or absolute local paths. The Windows/macOS Releases run the same upload entry after their own builds; credentials enter only the upload step, and when configuration is missing it is skipped explicitly. Whether the actual mappings can be used for Sentry symbolication must be accepted by new events at the receiver, and a successful build does not equal successful online symbolication.

Normal cancellation, source misses / temporarily unavailable, HTTP 4xx, mutual exclusion, ordinary warnings and generic logs without a stack are not sent and do not count toward failure counts. Plain-text failure receipts of background tasks stay on this machine; unexpected failures with an exception chain may be sent. SDK-internal logs do not enter the remote hook.

A failure of a given kind is uploaded immediately the first time within quota, and repeat counts are merged and submitted hourly or on normal exit. `occurrence_count` is the incremental count of this batch; for example, after uploading 1 and then 9 more occurrences, the next batch uploads 9, for a total of 10. `occurrence_day` is the UTC date on which it actually occurred, and `diagnostic_key` is computed from redacted technical fields; it includes the version but excludes the per-occurrence HTTP error ID, so the same code fault can be matched across machines, and it is not an installation identifier. Sentry's event count represents upload batches; for frequency, sum `occurrence_count` by statistics date rather than treating the latest batch as the cumulative total. Ordinary tags do not offer Sentry's native numeric summation; totals must be computed from the event fields, and Sentry's native event trend chart must not be taken as the true trend of occurrences.

Each machine is accepted at most 20 fault categories of local counts per day, and at most 20 remote batches per day are submitted; repeated backfill and the first diagnosis share the batch cap. The tray and the child service use the same file lock and aggregate file `state/remote-reporting-frequency.json`, keeping at most 7 UTC dates of technical samples, cumulative counts and enqueued counts; historical logs are not read. Pending submission counts for which quota was insufficient can continue to be submitted at a later startup or scheduled check, and expire after the retention period. After the SDK accepts a queueing, the enqueued count is updated; connection failure, server-side dropping, forced exit, lock contention or exceeding the category and retention limits can all cause gaps, so this is a best-effort fault count and not a complete runtime audit. Counts not yet accepted by the SDK are kept in the aggregate file.

`state/remote-reporting-delivery.json` stores the local receipt of the last batch for each technical purpose, and the configuration API's `remote_reporting.delivery` provides the same sanitized state. `queued` only means ready to enqueue; `accepted` means the transport got HTTP 2xx, which does not guarantee the receiver retains it long term; `failed` means explicit rejection or a block by the local queue/rate limit; `unknown` means no reliable result was obtained, and a network error may also occur after receipt. An HTTP 2xx that carries a rate-limit header is handled as unknown. The receipt stores no server body, request URL or payload; receipts of old events and old consent versions cannot overwrite the current record. A transport receipt does not rewrite the enqueued count into a received count, nor does it trigger resending.

Both are sent through a public DSN to the Sentry-hosted service, and the receiving service sees the connection IP. The client does not send an IP field, user identity, device identifier, watch history, media information, credentials, full logs or the diagnostic ZIP. The SDK send queue is not persisted to disk, and the local aggregate file stores only the technical projection and counts; the local consent version is rechecked before background sending. Turning it off or re-selecting clears unsubmitted aggregates and invalidates queued old events; requests already in flight or already received cannot be withdrawn. The local ZIP export works independently.

The receiver is configured by the maintainer: source runs use `PEACH_SENTRY_DSN` or `sentry.json` at the checkout root; Windows and macOS packaging and the Docker image have `scripts/write_reporting_config.py` write the package-root `sentry.json` from the environment variable of the same name (a build argument of the same name for Docker), located in the image under the wheel's `peach/_resources/`, and an environment variable of the same name set when the container runs takes precedence. The release pipeline reads them from the GitGud project CI/CD variables `PEACH_SENTRY_DSN` and `PEACH_LIBRARY_SENTRY_DSN`, both protected variables scoped to the `release` environment; when missing or invalid the release build fails, a local build writes empty values, and after installation the upload service is shown as not configured. Only Sentry's public HTTPS DSN (including the US / DE regions) is accepted, and no API token is needed. Without a DSN no SDK client is created. The SDK's automatic framework integrations, logs, performance tracing and metrics are all turned off; version statistics count as ordinary events against Sentry's error event quota. The account plan and totals follow the [Sentry subscription page](https://sentry.io/settings/).

Regression acceptance uses a temporary Peach data directory and an in-memory SDK receiver. Acceptance records of actual receipt and of release artifacts are kept outside the repository. For the technical diagnostics choice see [ADR-0110](adr/0110-recommended-diagnostics-choice.md). The installer helper process collects evidence only locally; it does not initialize a remote client or send events, and the application process sends according to the user's choice.

An `asyncio` connection cleanup is identified as connection-reset teardown only when all of the following hold: the `winerror` of the `ConnectionResetError` is `10054`, the callback is the standard library's `_ProactorBasePipeTransport._call_connection_lost`, the call stack contains only that callback and `asyncio.events._run`, and there is no associated exception. The handler checks that the real Proactor transport is in a cleanup state, closes the socket, deregisters it from the server and completes the closing state; it does not notify the protocol again. On success it records `classification=connection-cleanup` and `cleanup_recovered=true`, kept as local evidence only. If the teardown itself fails, the original exception chain is kept, a technical fault is reported, and the default handler is invoked; when the object state cannot be confirmed the default handler is also used. No Python class is modified globally and the event loop is not replaced.

The local record keeps the exception and standard library frames and adds the callback, protocol class, recognizable server category and TLS flag; these context fields do not enter the remote payload, and neither connection addresses, request content nor object text is accessed. Resource teardown uses CPython 3.14.7's private object protocol, so an upgrade must verify the actual socket, `asyncio.Server`, repeated close and teardown failure. The original race timing was not reproduced in 33 loopback experiments; synthetic faults verified that resources are actually closed and released by the server, which does not allow inferring the source of the original client.

### Remote error filtering review

The review covers the exception hook, logging, background tasks, sources, HTTP, media, browser, startup and update entry points. Filtering is based on structured state and the actual exception inheritance, not on error text, arbitrary same-named classes, or a blanket filter of all network exceptions.

A whole-file transcode's `TranscodeUnavailable` carries the bounded tool evidence and exit code of the last attempt, and keeps the process launch exception chain. The log entry uses the same media projection rules, sending only the structured exit code and the recognized `media_failure` category; raw tool text, media paths and attempt arguments do not enter remote events. Deliberate cancellation, timeouts and recognized media input conditions keep only a local record.

| State | Local and remote handling |
| --- | --- |
| Task cancellation, pause, mutual exclusion, billing and disk policy gates | Keep the local exception and task receipt, and do not use the error upload quota |
| Source cooldown, action budget, authorization, misses, explicit transient faults | Reuse source exceptions and classification, keep the local state; source parsing errors and unknown failures continue to be reported |
| HTTP client errors | Recognizes direct status codes, httpx responses and urllib HTTPError; 4xx stays local, and unclassified 5xx continues to be reported; `0` is not treated as an HTTP status code |
| Warning and retry logs | Logs below error stay local; error/critical carrying a Peach stack are reported |
| Media input and environment conditions | Bad media, missing input, permission, space and media tool timeouts stay local; missing tool executables, missing decoder capability and unknown technical errors continue to be reported; preview preconditions keep the prompt and retryable issue items |
| Browser cancellation and extensions | An AbortError from a deliberately cancelled request starts no record request; when the backend receives that type it still writes only locally; extension URL frames are not uploaded, and Peach script frames with build parameters keep the line and column |
| Client disconnect midway | The response header policy handles ASGI messages directly, and file responses stop sending after receiving the disconnect; server exceptions are passed as they are to the fault handler. Starlette's ClientDisconnect stays local and is not treated as a server program fault |
| Startup, CLI, tray, update and rollback | Unhandled technical faults continue to be reported; install helper processes keep the local-only diagnostic boundary |
| SDK, stackless logs and opaque browser errors | The SDK's own problems are not reported recursively; logs and browser errors with no Peach code location obtainable stay local |

The local policy does not clear existing Sentry events and does not control email; email digests and instant notifications are configured separately on the receiving side.

Both channels forbid low-level HTTP retries and redirects, keeping a finite number of sends and the DSN's receiving scope. Transport receipts are provided with the ZIP the user exports actively; the ZIP contains no local fault aggregate samples or research details.

### Library and taste cohort research

"Upload library and taste details" is a separate option, off by default, located at "App and maintenance → Data upload", with its own switch distinct from technical diagnostics. The switch is always visible. In settings the user generates a local preview, reviews the actual fields and content, and then consents explicitly; the preview count, size and excluded personal data are combined into one description. The server requires a one-time preview credential generated by the current process and valid for 10 minutes, the consent value and the field version. Flipping the switch on its own or enabling error diagnostics does not constitute library upload consent, and turning it off does not require a preview. The installer offers a separate option that is unchecked by default, with a short label summarizing the content and risk; after the user actively checks it, a scrollable page with the complete fields, purpose and risk description is shown, continuing means consent, and going back cancels the selection. The helper process only saves the choice; it does not read the library or initialize the SDK. Silent installation keeps an existing choice. The field version is `4`; consent for any other version is invalid.

The attachment `peach-library-taste.json.gz` losslessly compresses the following complete JSON:

- `schema`, `peach`, `period`: field version, Peach version and the UTC calendar week.
- `library`: one entry per canonical work code; when user signals exist, it carries the rating, like, dislike or watched, want-to-watch-later, cumulative play count, watch ratio and manual tags. Works without feedback send only the code, so collection coverage can be counted across deployments. Entries without a code do not enter the per-work list.
- `preferences`: performers, creators, studios, series, manual tags, five-year release-era bands and length bands, all grouped locally. Each group contains `name`, and, when matching library entries exist, `works` (deduplicated works that have a code) and `uncoded` (entries without a code). Each of the two scopes contains `collected`, `liked`, `disliked`, `watched` and `ratings` (a histogram from a 0–100 rating to a count); they must not be added together as a work count. Entities actively favorited additionally carry `favorite: true`. Explicitly registered male performers do not take part in person preferences. Length bands `0`, `1`, `2`, `3` are under 30 minutes, 30–90 minutes, 90–150 minutes, and 150 minutes or more respectively.
- `coverage`: `active_files`, `coded_files`, `coded_works`, `uncoded_items`, used to judge the coverage of the collection and rating samples.

Tags are taken only from the `web-user` evidence added one by one in settings, honor the hidden-tag preference; tags in entity favorites are the user's active choice and are also kept. Automatically scraped tags, technical tags and tags inferred from browsing behavior do not take part in this projection. Files with the same code are merged into one work: like and watch-later take the choice of any file, play counts are summed, the watch ratio takes the maximum of the saved watch ratio, the furthest play position and the cumulative play-duration ratio, capped at 1; feedback takes the most recent explicit mark by time. Ratings keep the 0–100 scale, empty values and 0 do not count as ratings, different valid ratings of different copies are averaged, and each work contributes a single rating per snapshot. Era and person associations are used only for local grouping and are not repeated per work.

No account, device or installation identifier, file name, path, media, URL, search term or per-entry browsing / watch record is sent. URLs, absolute paths and credential-like strings in tags and canonical names pass through the existing redaction function. The combination of works, ratings and grouped preferences may still be linked across submissions, or re-identified when matched with other data; Sentry sees the connection IP. "Anonymized" in the interface means removing direct identifiers and is not a guarantee of being unlinkable or of making the source unidentifiable. Linked uploads and knowing a real name are different judgments, and neither can be absolutely guaranteed.

The preview and background collection only read the ledger; they do not read browsing history, bookmarks or write preference caches. A large preview shows the first 24,000 characters in a code block, and the complete local JSON can be copied or downloaded. A preview is not a send and does not turn on upload; consent covers sending the latest snapshot with the same fields every week. After consent, the preview description, data preview and consent box collapse; the preview entry can still be reopened, and when already on, consent is not requested again. When the contract changes, `SCHEMA` must be advanced and consent obtained again.

The background reads details and initializes the SDK only when valid consent and the independent receiver both exist. A snapshot must contain at least one work with a public number or one preference group; when there is nothing to analyze it is marked `waiting-data`, rechecked every hour, and does not use up the weekly transmission chance. Failures before collection, compression or enqueueing can be prepared again. Each machine passes the final send gate at most once per UTC calendar week, reserved across processes with the same file lock; re-choosing consent does not reset the weekly limit. After actual sending, whether it explicitly failed or the result is unknown, no more is sent this week, and historical snapshots are not backfilled. An empty snapshot does not enter the research sample, and analysis results must disclose this selection basis.

`state/library-sharing-attempt.json` distinguishes `waiting-data`, `queued`, `accepted`, `failed`, `unknown` and `blocked`, and `attempted` indicates whether the final send gate was passed. The settings API's `last_attempt` provides only the receipt of the current UTC week, and does not rewrite the original record across weeks. `accepted` proves only that HTTP 2xx was obtained; not obtaining an HTTP receipt, network interruption and historical records with no receipt are none interpreted as successful receipt. Queues of old field versions, old UTC weeks and old consent versions cannot send; an old attempt receipt cannot overwrite a new attempt.

The raw JSON limit is 100 MiB and the gzip attachment limit is 18 MiB; exceeding either rejects the whole thing, and no truncated data is sent. The gzip header contains no source file name or generation time. Transport accepts only fixed-purpose events, fixed-file-name attachments and a field whitelist, and the consent version is rechecked before the background actually sends. Turning it off invalidates queued records, and data already sent cannot be withdrawn through the local switch.

The maintainer separately sets `PEACH_LIBRARY_SENTRY_DSN`, and both packaging ends write it into the package's `library_dsn` as described above. This DSN's project must differ from the error diagnostics project, and the same project is treated as not configured. Research snapshots are received as Sentry attachments and also produce one event each time; event and attachment quotas within the organization are still shared. See the [Sentry attachments documentation](https://docs.sentry.io/platforms/python/enriching-events/attachments/).

Cohort analysis aggregates, separately by `period`, work ownership rate, work rating distribution, performer and series preferences and manual tags; each snapshot contributes ownership once per work, and an entity's `favorite` means actively favorited while `collected` means owning related works, so they must not be mixed. Ratings use the number of valid raters or ratings as the denominator; unrated must not be treated as a 0 score, and file counts must not be treated as user counts. A weekly snapshot is a cumulative state and cannot be summed across weeks into new collections or plays. There is no cross-period identifier, but this does not justify claiming the details cannot be linked; once per machine per week also cannot identify the same person across multiple installations. Results represent only the voluntarily participating sample, and installation coverage and selection bias must be stated. The receiving-side analysis dashboard is not part of the client upload feature.

## ZIP contents

The diagnostic report and the scraping records on the system diagnostics page are both generated in the background, with progress shown by the candidates and source snapshots actually read; they can be cancelled, and after refreshing the page you can continue to view the task in the same service. When complete, the file is read through a download link. Generation and ZIP merging are written to a temporary file in chunks, unfinished artifacts are cleaned up on cancellation, and regenerating reclaims that manager's previous artifact. After a service restart it must be generated again.

The ordinary diagnostic report automatically merges detailed scraping records not exceeding 100 MiB after compression, and when over the limit keeps a summary and prompts to export separately by product code. Scraping records accept up to 20 product codes, and when left empty read recent works, including source fields, candidates, current ownership and review decisions; only existing data is read. Automatic error forensics attaches only the scraping summary and does not generate the full scraping records in the background.

The background export endpoints are `GET/POST /api/diagnostics/exports`, `POST /api/diagnostics/exports/{job_id}/cancel` and `GET /api/diagnostics/exports/{job_id}/download`, all keeping the login and local admin checks, with write requests checked for same-origin. The state is `idle`, `running`, `cancelling`, `complete`, `cancelled` or `failed`; download accepts only the identifier of the currently completed task.

`GET /api/diagnostics/bundle` directly returns the regular logs and diagnostic summary; detailed scraping records are generated through the background export.

- `report.json`: system and version information, check results, media tool capabilities, source health summary and file collection receipts.
- `logs/<directory index>/`: tray, service, restart, first scan, source update, tunnel, error and crash logs; fixed logs include recent calendar-month segments. When a page operation is rejected by the API with 400 (for example, the library does not find the product code when manually fetching a cover), the rejection reason is written to the `http-request` record in `errors-*.log`, stays local, and is not reported remotely.
- `processing/`: library processing state and the recent issue list, startup preparation, automatic updates, standalone package updates and tunnel state.
- `updates/`: recent update migration logs.
- `covers/`: per-product-code cover processing results from the discovery page (`feed-cover-attempts/<product code>.json`) and metadata task state; the metadata cache itself stays local.
- `scraping/`: the source summary, plus field candidates, ownership and source snapshots within the merge limit; credentials and media paths are sanitized.

Each file is read for at most the last 96 KiB; at most 8 error logs, 4 crash logs, 8 processing issue lists and 2 migration logs, and the 500 most recent cover processing results by modification time. Truncation and read failures enter the collection receipt, and a single unreadable file does not affect other evidence. JSON and JSONL are parsed separately, and a partially written trailing line does not enter the shared report. The log retention period follows the half-year and calendar-month segment policy.

The ZIP does not contain the ledger, configuration files, private keys, login cookies or media files. Paths, URLs, addresses, credential fields and command-line credential values are sanitized, and dictionary keys are sanitized as well: keys of the form `<asset number>:<path>` keep the number prefix, and keys with the same name after sanitization get a sequence suffix such as `#2`; media names and `path` fields in processing records are hidden as whole values, keeping only the asset number and carrying out no library list. The default logs of fault injection land in the test process's temporary directory.

## Media tools

AV1 frame capture needs a working software decoder. `scripts/build_ffmpeg_windows.sh` statically builds in a pinned dav1d; the full source archive, license and SHA256 manifest are verified through `media_tool_bundle.py --validate-only`.

Release acceptance uses an embedded synthetic AV1 clip, decoded and frame-captured on the CPU, independent of the machine's graphics card or AV1 encoder. Failure records, file fingerprints and retry results for real media are kept in private diagnostic records outside the repository.
